# Mission Queue and Runner

This page describes the server-owned Mission queue, runner lifecycle, delivery guarantees and
generated worker projection.

> Last updated: 2026-11-12

## Queue Authority

`runner-queue.js` stores queue metadata, ordered items, numeric revisions and durable events in
SQLite. `runner_queues` owns the revision and custom instructions; `runner_queue_items` owns
stable item IDs, order, plan path, status and reason; `runner_queue_events` records accepted
mutations. Writers submit the revision they read. A stale revision returns
`queue_revision_conflict`; the server never silently retries or overwrites a draft.

Two writers are exempt from hand-resolving that conflict, because their writes commute with
whatever moved the revision. The page's **Add plans** re-reads the queue once and retries, and
the worker tool `agent_queue_update_item` retries once against the current revision. The
worker's write is guarded by ownership instead (its assigned item, a legal status step): a
running worker bumps the revision on every status update, and a human adding a plan mid-turn
bumps it under the worker.

Membership and order change only while the runner is `paused` or `complete`
(`queue_runtime_busy` otherwise), with one exception: plans may be **appended** while an ordinary
queue operation is dispatching or running, and while the queue waits for input, since an append
never disturbs the item the worker holds. Reorder and removal still need a pause, and the page
disables those controls with the reason. The rule is one function,
`runner-state.queueEditVerdict`, called by both the write and the view. Nothing may be changed during a blocker resolution, which is pinned to the revision
it was sent against.

`QUEUE.md` is generated worker output, not queue authority. Workers read and update through
`agent_queue_read` and `agent_queue_update_item`; they never edit the file. A changed projection
sets `projection_error`, keeps canonical rows visible and blocks dispatch. Regenerate rewrites
the output from canonical rows, invalidates the old operation and leaves the runner Paused. It
does not import file statuses. A human may correct one reviewed item through the status-review
operation, which publishes the canonical change under the same revision check.

Because a runner overwrites its queue file, it may only claim a file that is safe to replace.
`plans.assertQueueFileClaimable` runs when a runner is created and when its queue file is
renamed. It refuses `INDEX.md` and `README.md` (`runner_queue_file_invalid`), and any existing
non-empty file that lacks the `> Generated by Paddock.` line (`runner_queue_file_exists`). A
missing file, an empty one, or one Paddock generated earlier is accepted. Plan writes apply the
matching rule from the other side: the reserved names `README.md`, `INDEX.md` and `QUEUE.md` are
checked against the resolved path, so `./QUEUE.md` or `x/../INDEX.md` cannot be written as a plan.

The numeric queue revision and the projection content hash answer different questions. The
revision detects a competing canonical mutation; the hash detects generated-file drift. The
write-boundary guard compares the current canonical revision with the revision read for the
dispatch, then independently checks projection integrity.

### Queue File and Custom Instructions

The queue file is a per-runner setting (`infinite_runners.queue_file`, Settings → Queue file),
default `QUEUE.md`. `plans.normalizeQueueFile` accepts a relative Markdown path inside the
project's plans folder, such as `release.md` or `queues/release.md`; blank means `QUEUE.md`.
Absolute paths, `..` escapes, symlink escapes, NUL bytes and non-`.md` names fail with
`runner_queue_file_invalid`. Every consumer derives the path from the runner: projection, marker
(`QUEUE.paused` stays in the plans folder root), prompts and callbacks. Changing the file is
refused with `runner_queue_file_busy` unless the runtime is `paused` with no owned operation. The
old file is left as it was, and the new one must also be claimable.

Custom instructions are optional queue-level guidance (`runner_queues.custom_instructions`, at most
16 KiB, `PUT /api/mission/runners/:id/queue/custom-instructions` under the queue revision). They
are not template syntax: [Runner Prompt Templates](runner-prompts.md) appends them literally to
every dispatch in a labelled section. Saving them sends nothing; they apply at the next dispatch.
An empty string removes them.

### Queue Summary

`plans.queueSummary` is the one projection of `current` (first in-progress item), `next` (first
`new` item), `blocked` (first need-input item), `counts`, `allDone` and `warnings`. Both the page
and the scheduler read it. An empty queue is valid and not complete: `allDone` needs at least one
item. More than one in-progress item is legal: it adds a `queue_multiple_in_progress` warning
naming the items, the page shows it above a still-visible list (`msn-queue-warning`), and the
runner resumes the first one in order.

**Add plans** lists the project's plans folder (`GET /api/mission/runners/:id/plans`) with title
and status; the server leaves out `INDEX.md`, `README.md` and `QUEUE.md`, and the picker hides
completed or archived plans behind a toggle. Selection order is the order appended. Adding plans
never starts work.

## Runner Sessions

An infinite runner is an ordinary Mission session with a queue attached. Opening a conversation
and running its queue are separate actions:

- Creating a runner mints or binds a real session. On a stopped PAD the create fails whole; no
  runner row is left behind. Converting an existing session keeps its row, conversation id, lock
  and terminal.
- The Sessions list renders the bound session with the shared row component, the runner name and
  an ∞ badge, sorted before ordinary sessions and counted once. A runner with no session yet
  renders the same-shape row (`no session yet`). Each runner row carries a Configure gear
  (`msn-btn-runner-config`).
- Clicking a runner row opens its terminal in column 3, never the settings dialog, and never
  starts the queue. `POST /api/mission/runners/:id/session` (`ensureRunnerSession`, serialized per
  runner) creates the session for an unbound runner or recovers a dead one in the same
  conversation, and enables nothing.
- Run and Pause live in the terminal header (`RunnerControls`) and change only the queue; the
  terminal stays mounted.
- Closing the bound session stops its runner first (`disableRunnerForSession`), so a watcher
  cannot resurrect a session that was closed on purpose.
- Remove (Configure → Remove) deletes the runner and keeps the session, its live pane and the
  queue file; the row returns to the ordinary list.

## Execution State

`runner_runtime` is the only authorization state. `runner_operations` owns each durable attempt;
`runner-transition.js` checks its state, generation and operation identity transactionally.
The UI consumes the server's `execution` and `scheduler` snapshot instead of reconstructing a
verdict from legacy columns or item progress.

| State | Meaning | Available action |
|---|---|---|
| `setup_required` | Canonical runtime or queue setup is absent | Set up; Run is unavailable |
| `paused` | No work is authorized to dispatch | Run explicitly or edit/review the queue |
| `dispatching` | One durable send attempt owns the runner | Pause or Close |
| `awaiting_receipt` | A write may have landed, but its exact receipt is absent | Reconcile, Hold, Pause or Close |
| `running` | The exact instruction receipt is confirmed | Pause or Close |
| `waiting_input` | A specific queue item or provider blocker needs a person | Resolve or review, or Close |
| `held` | An uncertain operation is stopped after its deadline | Inspect, Reconcile or Run fresh |
| `complete` | All queue items are done | Add work; the runner returns to Paused |
| `projection_error` | Generated output differs from its acknowledged version | Regenerate; Run is disabled |

### The view the page renders

`services/runner-view.js` builds `execution` with one pure function, `buildExecution`. It reads
no database: the caller passes the runtime state, queue condition, items, scheduler decision,
active operation, pause mode and whether the worker is mid-turn. The page renders the result
and derives nothing.

| Field | Meaning |
|---|---|
| `state` | Runtime state; a queue repair condition (`projection_error`, `setup_required`) wins |
| `label`, `tone` | Header word and its colour family (`active`, `success`, `danger`, `idle`) |
| `reason` | One sentence for the status strip |
| `banner` | `{ kind, tone, text }` shown above the list, or `null`. Paused only, today |
| `operation` | The operation that owns the runner, or `null` |
| `actions` | One `{ allowed, reason }` per control; `reason` is the disabled tooltip |

`actions` carries `setup`, `run`, `pause`, `regenerate`, `reconcile`, `reviewStatus`,
`resolve`, `addItems`, `reorder` and `removeItem`. Each is computed from the predicate the
write path enforces, so an offered control is an accepted write:

- `run` uses the state machine's `EVENTS.run`.
- `addItems`, `reorder` and `removeItem` use `runner-state.queueEditVerdict`, the same call
  `runner-queue.mutate` makes before any change.
- `reviewStatus` uses `REVIEWABLE_STATES`, which `updateRunnerQueueItem` also enforces
  (`runner_invalid_state` otherwise).

`runner-view.test.js` pins the parity by attempting each write in every state on a throwaway
database and comparing the outcome with the verdict.

When an interrupted turn is verified idle, `scheduler.recoveryRequired` is true, `actions.run`
is allowed and `actions.pause` is not: the page offers an explicit recovery Run. A normal active
turn keeps Pause available. `working`, `idle` and `unknown` describe worker observation
separately from authorization; an unreadable or unknown observation never means idle.
`scheduler.countdownLabel` names a running countdown (idle grace, nudge interval) so the page
only keeps the clock.

A refusal raised by an action taken inside a dialog renders inside that dialog
(`components/ui/DialogError.jsx`): plan picker, status review and resolve.

### When the next plan is sent

The watcher (`mission/scheduler.js`) runs one pass every 20 seconds for each runner in `running`
or `awaiting_receipt`. For a `running` runner, a pass sends the next plan only when the worker's
turn is verified idle and no instruction is outstanding. For an `awaiting_receipt` runner, the
pass only reconciles the outstanding operation (see Operation Delivery) and sends nothing.

- **The worker reported the assigned plan done.** The next plan is sent on the first pass after
  its turn ends. The idle grace and nudge interval do not apply: the send starts a new plan, it
  is not a nudge. The assigned plan is the active operation's `item_id`.
- **The worker went quiet without reporting.** The pass waits out `idle_grace_ms`, then
  `min_nudge_interval_ms` since the last send, then nudges, up to `no_progress_budget` times.

The nudge count (`retry_count`) is the number of consecutive nudges sent for an unchanged queue.
A send for the revision the last instruction was already sent for adds one. Any other send sets
it to zero: a send for a changed revision, an explicit Run, a pane recovery, a quota recovery.
Conversation activity alone does not reset it, so a worker that answers every nudge without
touching its plan still reaches the budget, and the runner stops in `waiting_input` with "No
progress after N dispatches".

"The queue changed" is a numeric comparison (`sameRevision`). `last_dispatch_revision` is a TEXT
column and a bound JavaScript number is stored as a float, so revision 2 reads back as the string
`2.0`. Compared as strings or with `!==`, the stored and live revisions are never equal, every
send counts as a new revision and the budget can never run out.

A worker `done` also starts a **fast watch** (`kickRunnerWatch`): every 750 ms, for up to 90
seconds, it reads the worker's turn from the agent's store and runs an ordinary pass once the
turn is idle. It decides nothing itself. One fast watch exists per runner generation, so a
pause, a new Run or the dispatch it caused ends it, and a report for the next plan replaces a
loop left over from the previous one. Passes for one runner never overlap in a process
(`watchRunner`), and a pass that loses the dispatch compare-and-swap sends nothing.

Measured on `devrunner` with both timers at their 120-second default: `done` at 12:44:49.5,
turn ended 12:44:52.038, `dispatch_next` 12:44:52.041. The last plan's turn end and `complete`
shared a timestamp.

While a queue is running the page re-reads it every 3 seconds; otherwise it follows the page's
15-second poll.

### Operation Delivery

Before sending, Mission persists an operation ID, generation, conversation ID, item assignment,
queue revision, normalized prompt hash, baseline input ID and deadline. A unique runtime CAS
gives concurrent Run, watcher and recovery attempts one owner. Immediately before the terminal
write, Mission rechecks the operation lease, runner/session binding, lock, worker turn and queue
revision after asynchronous preflight. Pause, Close, solo lock, a new human turn or a changed
binding cancels the reserved send.

A receipt is a new user-message ID in the bound conversation after the baseline, with the exact
normalized prompt hash. A pane repaint alone is not a receipt. Unknown delivery stays
`awaiting_receipt` and is never automatically resent. Reconcile may confirm only that operation
in that conversation; a verified-idle operation past its deadline becomes `held`. The deadline is
10 minutes after the send (`RUNNER_NO_RESPONSE_TIMEOUT_MS`). The watcher runs this same
reconciliation on every pass over an `awaiting_receipt` runner, so a receipt that lands after the
5-second wait is confirmed without anyone pressing Reconcile. Reconcile on a runner that is
already `running` answers `alreadyConfirmed` and changes nothing. Hold retires
receipt eligibility. Run fresh creates a new operation; a late receipt cannot revive the old
one. A confirmed instruction remains outstanding through its complete turn, not merely a tool
step, before another item can be dispatched.

Current-task Pause sends one cooperative stop request and remains `requested` until the worker
is observed idle. It keeps the current item `in_progress` at its checkpoint. Polling does not
repeat the request. Quota recovery and pane-loss recovery use the same generation and operation
ownership rules; a superseded callback cannot restart or send into a newer runner state.

A turn the agent's store reports as `working` is treated as over once its pane is known to be
gone (`interruptedByDeadPane`): nothing is left to finish it, and the store would say `working`
indefinitely. A watch pass that finds the pane dead restarts the worker in the same conversation
and sends the `recovery` prompt, while `recover_exited` is on and `recovery_count` is below
`recovery_budget`; past the budget the runner becomes `held`. When recovery has to wait, the
runner's reason says why ("Worker pane is gone; recovery is waiting: …"). An explicit Run applies
the same rule, so it does not answer `runner_worker_not_idle` for a worker whose pane is gone.

Closing the worker's session stops its runner first, on both paths (`closeSession` from the page
and `endSession` from the Mission tools). Killing the pane first would let the next watch pass
see a dead pane and restart the TUI in a session that was closed on purpose.

Provider quota exhaustion is read from the worker's live screen and from its conversation store
by a separate observer. A definitive screen notice moves an active runner to `waiting_input` with
the cause `usage_exhausted`. [Backend services](services.md) describes what counts as a notice.

### Pause Modes

`POST /api/mission/runners/:id/pause` takes `mode`; the page offers both in the Pause queue
dropdown. Both stop dispatch at once and leave the terminal and conversation alone; an unknown
mode fails with `runner_invalid_pause_mode`.

| Mode | What the worker is asked | Confirmed when |
|---|---|---|
| `before_next_task` (default) | Nothing; it finishes the plan in flight | The target item is no longer `in progress`, or there was none |
| `current_task` | The `pause` prompt: checkpoint progress and resume notes into the plan file, keep the item `in progress`, stop | The worker's turn is observed idle |

`infinite_runners.pause_mode`, `pause_state` (`none`, `requested`, `confirmed`) and
`pause_target_item` record the request. `pauseConfirmation` is a pure predicate, applied on each
queue read; an unreadable observation stays `requested`, so the page never claims a stop it did
not see. `current_task` with nothing in progress degrades to `before_next_task`. A stop message
that cannot be confirmed says so in the reason ("Pause requested — delivery unconfirmed"). The
next Run after a `current_task` pause sends the `resume` prompt naming the paused plan; any
successful Run clears the pause record.

### The Stop Marker

`QUEUE.paused`, in the plans folder, is a worker instruction: every prompt tells the worker not to
start an item while it exists. `runner-state.markerRequired` decides it from the runtime state
alone:

| Marker present | Marker absent |
|---|---|
| `paused`, `waiting_input`, `held`, `complete`, `projection_error` | `dispatching`, `awaiting_receipt`, `running` |

Run lifts the marker before it types the startup prompt; otherwise the worker would read it and
refuse its own instruction. An unconfirmed delivery (`awaiting_receipt`) keeps the marker absent,
because restoring it would tell a worker that did receive the prompt to stop, and no receipt
could ever arrive. Only a definite pre-write refusal, a hold, Pause or Close restores it. A failed
marker write is stored in `marker_sync_error` and shown, never swallowed. Each stop also records
its cause and origin (`stop_cause`, `stop_origin`, `stop_at`), so an automatic stop (blocker,
quota, invalid queue) never reads as the user's Pause. Removing a runner leaves the marker in
place so a detached worker cannot take another item.

### Explicit Run

Run is an explicit control intent, separate from whether an instruction may be sent:

- **Paused, worker verifiably working, queue in progress:** Run adopts the active turn
  (`adopt_active_turn` to `running`), lifts the marker and sends nothing. This is the path after
  a human typed into the session, or after an answer started a turn.
- **Running, worker turn ended in an error:** `scheduler.recoveryRequired` is set, the page shows
  Run queue instead of Pause queue, and Run retires the interrupted operation and sends one fresh
  instruction. The watcher never does this on its own.
- **Running otherwise:** Run answers `already_running`.
- **Paused, held or complete:** Run validates the queue and an idle worker, then dispatches the
  `start` or `resume` prompt under a new operation.
- **Stopped by a provider quota (`waiting_input`, code `usage_exhausted`):** the page labels it
  **Usage limit** (warning tone, `banner.kind: 'usage_limit'`), not "Needs input" — nobody asked
  a question, so there is nothing to answer — and offers Run. With a `usage_exhausted` recovery
  script configured, Run queues that script (quota recovery). Without one, Run reads the
  worker's screen with the same detector that stopped it (`provider-limit.js`): while the notice
  is still there it refuses with `runner_quota_still_exhausted` (409) and sends nothing; once it
  is gone it records `usage_recovered`, leaves the stop through Pause, and continues as a normal
  Run (idle worker → start prompt; a turn the worker already began → adopted).
  The watcher also lifts the stop by itself (`observeQuotaStops`, every 20 s callback tick) once
  the provider has demonstrably answered since the stop: the notice is gone from the worker's
  screen AND the worker's store shows a turn that finished after the stop. A notice that is only
  hidden (a dismissed modal) does not count, nor does a turn still running. The lift is a
  `startRunner` with actor `quota-observer`, so every gate of an explicit Run applies; a runner
  whose recovery script is in flight is left to it.
- **Store says the worker is still working, but nothing runs the turn:** on an explicit Run, a
  turn that reads `working` in the store, has not moved for 2 minutes (`WORKER_STALL_MS`), and
  whose live pane does not show the driver's busy marker (`tuiBusyPattern`; opencode's
  `esc interrupt`, present for exactly as long as a turn runs) is treated like a dead pane: not
  adopted, not blocking, recorded as `worker_stalled`. The write boundary (`beforeWrite`) accepts
  that same abandoned turn only while it is unchanged (same input, same `progressAt`); any
  progress or new input withholds the send. This is the turn a provider quota error leaves
  behind: opencode never marks the step complete. The watcher never applies this on its own.

A pane that is already gone is never adopted as a working turn.

### Worker Observation by Driver

`agentStore.readTurn` answers the same shape for all three coding drivers: `state`
(`idle` / `working` / `unknown`), `userId` (an id that changes with every new input), `inputHash`
(sha256 of the input text, trailing whitespace trimmed: the exact-receipt match) and
`progressAt` / `completedAt`. `unknown` withholds every automatic send.

| Driver | Store | Turn open → closed | Input id |
|---|---|---|---|
| opencode | `opencode.db`, by primary key (~2 ms) | newest assistant step `finish: stop` with `time.completed`; an `error` is an interrupted turn | message id |
| codex | `rollout-*-<id>.jsonl` | `event_msg/task_started {turn_id}` → `task_complete` (idle) or `turn_aborted` (interrupted) for the same `turn_id` | `codex:<line>` of the `event_msg/user_message` |
| claude | `<id>.jsonl` | a human `user` row → `system/turn_duration` (idle) or `[Request interrupted by user…]` (interrupted) | `claude:<uuid>` of that row |

The codex and claude readers live in `services/jsonl-turn.js`. They find the transcript by the
id in the FILE NAME only (never "the newest file"), and read incrementally: each file keeps its
folded state and byte offset, so a 300 ms receipt poll parses only the appended bytes, and a
half-written last line waits for the next read. A codex input comes from `event_msg/user_message`,
never from `response_item` user messages, which carry injected context. A claude human input is a
`type: user` row that is not `isMeta`, not `isSidechain` and carries no `tool_result`; slash
command wrappers are skipped. claude writes `turn_duration` only from CLI 2.1.318, so on an older
CLI an open claude turn is `unknown`, not `working`. An interrupted turn on any driver is `idle`
with `outcome: 'error'`, which requires explicit recovery.

A fresh codex worker has no conversation id until its first message creates the rollout. The
dispatch gate (`canDispatch`) first tries to adopt it (see
[Mission Page](../pages/mission.md#launching-the-tui)); adoption updates the session object in
place, so the same pass dispatches and stamps the operation with the real id. When nothing has
been typed yet the gate refuses with `runner_worker_identity_unavailable` and says to type
anything into the session and press Run again; when several new conversations in the folder fit,
it says so instead of guessing. The runner never sends into an id-less session: every receipt and
ownership check compares conversation ids, and a send it cannot match would be a blind one.

One limit remains: usage-exhaustion evidence from
the store (`readUsageEvidence`) is still measured for opencode only; on codex and claude the
screen notice (`provider-limit.js`) is the only exhaustion signal. No driver exposes compaction
in its store, so it is not inferred.

### Plan File

The Mission file viewer reads and edits one plan through `readRunnerPlanFile` /
`writeRunnerPlanFile` (`runner-queue-api.js`). The path is relative to the project's plans folder
and resolved by `plans.planPath` on the host (through the webui's bind mounts, so it works while
the PAD is stopped); a path that leaves the folder, is not `.md`, or is a reserved name
(`QUEUE.md`, `INDEX.md`, `README.md`) is refused with `plan_path_invalid` / `plan_reserved_name`.

- The file is edited **raw**, frontmatter included, up to 2 MiB.
- Edit only: a missing file is `plan_not_found`; creating plans stays with the plan tools, which
  stamp the frontmatter a new plan needs.
- `revision` is the sha256 of the content read, and a save must present it. A changed file is
  `plan_revision_conflict` (409) and nothing is written: the worker edits its own plan while it
  runs, and a save over an edit the human never saw would discard the agent's work. The viewer
  keeps the human's text and offers Reload.
- The write goes through `writeFileOwned`, so the file keeps its PAD-side owner.
- The audit row `plan_file_saved` records the path and byte count, never the text.

## Projection Publication

`runner-publication.js` owns filesystem output, marker writes, acknowledgement and publisher
leases. Queue mutations record the desired projection revision/hash in the same transaction as
canonical rows and events; runtime transitions record the desired marker with the state event.
The publisher writes atomically, checks that the desired version still matches, then acknowledges
that exact version. The lease serializes publishers across webui processes, and a runner cannot
claim another runner's projection or marker path.

A publication failure remains visible and withholds dispatch. Boot retries an unacknowledged
desired version, but never overwrites an external edit to an already acknowledged projection.
Queue-path changes invalidate the old acknowledgement through the publisher service. The additive
schema update adds `operation_kind` and `queue_revision`; historical operation rows keep NULL
values rather than receiving guessed data.

## Worker and Mission APIs

Worker tools require the exact `runner_id` and the assigned item. `agent_queue_update_item`
accepts `new`, `in_progress`, `need_input` or `done` under a numeric revision. A worker cannot
resolve its own blocker. Every prompt includes the mandatory server queue protocol, including
saved custom prompts; unavailable tools mean stop, never file editing.

## Two MCP Surfaces

| Server (in the pad) | Endpoint | Credential | Tools | For |
|---|---|---|---|---|
| `paddock` | `/mcp` | user API key (grants) | the full control surface, including all five `agent_queue_*` tools | humans, orchestrators |
| `paddock_runner` | `/mcp/runner` | per-pad runner token (`prk_…`) | `agent_queue_read`, `agent_queue_update_item` only | infinite-queue workers |

A runner token (`runner_mcp_tokens`, sha256 only, one per pad; minting replaces the old one)
identifies a **pad**, not a user. It reaches only runners whose project lives on that pad; anything
else returns `runner_not_on_this_pad`. User API keys are refused on `/mcp/runner` with a JSON 401.
Queue events written through it carry the actor `runner-mcp:<pad>`. In opencode the tools appear as
`paddock_runner_agent_queue_read` / `paddock_runner_agent_queue_update_item`, which is how the
prompts name them.

Nobody wires it by hand. On Run, `ensureRunnerMcp` probes `paddock_runner` (`opencode mcp list`, as
the pad user). If it's connected, nothing happens. If it's absent or failed, Run mints a token,
removes any stale entry, runs `opencode mcp add` with the token read from stdin (never argv), and
re-probes. MCP servers load when a TUI starts, so if the wiring changed and the bound worker TUI
is live and idle, Run restarts it into the same conversation (`worker_restarted`). If the worker is
mid-turn, Run refuses rather than interrupting it.

## Worker Readiness and Delivery

Run checks the worker before it types anything, and refuses with a code that names the fix:

| Code | Meaning |
|---|---|
| `runner_worker_tools_missing` | Automatic wiring of `paddock_runner` didn't connect; the message quotes opencode's reason and points at `HOST_NAME` (the pad must reach this host). An unreadable probe (`unknown`) neither wires nor blocks. |
| `runner_worker_identity_unavailable` | The worker session has no conversation id, or the runner is bound to another session. Close the worker and Run again. |
| `runner_worker_locked` | A human has solo-locked the worker session. |
| `runner_worker_not_idle` | The worker is mid-turn. |

A refusal is returned to the caller; it does not replace the reason a stopped runner already
shows. While the runner is `waiting_input`, `held` or `projection_error` with a reason code other
than `runner_notice`, `setRunnerReason` leaves both the code and its text alone. Quota recovery
recognises its runner by the `usage_exhausted` code, so a refused Run must not erase it.

Every session carries a conversation id from its first read. On a published pad the id is minted
through the pad's web server; on an unpublished pad (the default) the driver starts a short-lived
`opencode serve` on a random loopback port as the pad user, `POST`s `/session` for the folder, and
stops it (~4 s). It logs to stderr because the running TUI holds the log file.

`sendText` waits for the driver's `tuiReadyPattern` (opencode: the `ctrl+p commands` footer hint,
or a footer line ending in `commands` on a pane too narrow for the hint; shown both idle and
mid-turn; a pane of 120+ columns puts sidebar text after the hint on the same line) before writing, for up to 15 s. A freshly launched TUI drops input for its first ~5 s,
and that is where every new worker's startup instruction used to go. A TUI that never becomes ready
gets `mission_tui_not_ready` with `attempted: false`, meaning nothing was written and a retry is safe.

After the write, the runner polls for 5 s for the exact receipt: a new user message whose text
hashes to the instruction. It stops early if Pause, Close or a newer operation takes ownership.
`sendText` confirms on new store activity, which can land before the user message's parts can be
read, so a single read reported delivered instructions as unconfirmed.

Pause invalidates the owned operation immediately, but the item it interrupted may still be
**closed** by the worker while the runner is paused (`in_progress` to `done` or `need_input`).
That is what lets "Pause before next task" finish the plan in flight; before it, the worker's
closing write was refused with `queue_item_not_assigned` and the row stayed Working until the
next Run. Starting any item while paused is still refused.

An automatic dispatch withheld at the write boundary (lock, queue revision moved, projection
drift, a new human turn) pauses the runner once and logs one `dispatch_failed`. Later watcher
ticks do not retry it; only an explicit Run resumes. Pre-113 code retried such a refusal every
nudge interval indefinitely.

`publicRunner` (served by `/api/mission/runners`) never contradicts the canonical runtime. When no
session is bound, the worker fields read `unknown`. When the runtime is inactive, the
`scheduler_*` fields follow `execution.state`, so a stale idle-grace countdown does not outlive
its run. Internal scheduling still reads the raw columns.

## Blocker Resolution

A worker that needs a person sets its item to `need_input` with the question in `reason`, and the
runner stops in `waiting_input`. The answer goes through one server operation,
`POST /api/mission/runners/:id/resolve` with `itemId`, `answer`, `revision` and an optional
`idempotencyKey`. The client never sends the answer, requeues and starts in separate calls: the
answer makes the worker busy, so a following Start was refused and the queue stopped.

1. Check: the runner is `waiting_input`, or `paused` with that item still `need_input` (a pause
   the plan outlived by asking); it then moves to `waiting_input` first. The queue must be
   readable, blocked on input, and at the submitted revision (`queue_revision_conflict`
   otherwise; it is never retried blindly).
2. A repeated `idempotencyKey` returns the earlier outcome without sending. A row in
   `runner_resolutions` reserves the resolution; a concurrent one fails with
   `resolution_already_pending`. An omitted key is stored as `NULL`, not `''`: the table's
   `UNIQUE (runner_id, idempotency_key)` would otherwise allow one keyless resolution per runner
   for its whole life.
3. The answer becomes a `resolution` operation (`resolve_begin`) with its own prompt hash,
   baseline input and deadline. The marker is lifted. Right before writing, the runtime, session
   lock, conversation and queue revision are checked again; a changed blocked item aborts with
   nothing sent.
4. The answer is sent to the bound Mission session as one line, `Resolution for "<plan>":
   <answer>`, normalized like every prompt and hashed as sent. A multi-line answer would arrive as
   several messages, none of which matches the receipt hash.
5. On an exact receipt the runner moves to `running`, the item is requeued to `new` under the
   current revision, and the resolution is `completed`. The watcher then waits for that turn to
   end and continues the queue with no second Run.

An attempted write without a receipt returns `awaitingReceipt: true` and leaves the runner in
`awaiting_receipt` with the marker absent. Nothing is resent. When the watcher, or Reconcile,
later finds the exact receipt, it requeues the item if it is still `need_input` (refusing if the
queue moved in between) and completes the resolution. An answer that definitely did not go out
leaves the runner in `waiting_input` with the reason `resolution_failed`, the marker restored and
the answer still in the dialog, so it can be sent again. A later Pause wins: a late receipt
cannot re-enable a paused run.

In the queue panel the inline answer field and the Resolve blocker dialog share one draft, keyed
by runner and blocked item, so text typed inline is already in the dialog. Enter in the inline
field opens the dialog and Enter in the dialog sends; both skip IME composition. Closing the
dialog keeps the draft without a "Discard changes?" prompt; only leaving the session with an
unsent answer asks. Success and failure show as operation feedback, and a failed send keeps the
dialog open.

## Runner REST Surface

All routes resolve the runner, then check access to its project and PAD (`missionRunner`); writes
need CSRF.

| Route | Purpose |
|---|---|
| `GET /api/mission/runners` | Runners for the all-projects view |
| `GET /api/mission/runners/:id` | One runner with its enriched queue |
| `PATCH /api/mission/runners/:id` | Name, queue file, timings, budgets, prompt templates; never starts work |
| `POST /api/mission/runners/:id/session` | Create or recover the worker session; enables nothing |
| `GET /api/mission/runners/:id/queue` | Canonical rows, revision, summary, `execution`, `scheduler` |
| `POST /api/mission/runners/:id/queue` | Set the queue up |
| `POST /api/mission/runners/:id/queue/items` | Append plans (`plans`, `revision`) |
| `PUT /api/mission/runners/:id/queue/order` | Reorder (`itemIds`, `revision`) |
| `DELETE /api/mission/runners/:id/queue/items/:itemId` | Remove one item |
| `PATCH /api/mission/runners/:id/queue/items/:itemId` | Status review of one item |
| `PUT /api/mission/runners/:id/queue/custom-instructions` | Queue guidance |
| `GET /api/mission/runners/:id/plans` | Candidates for Add plans |
| `GET /api/mission/runners/:id/plan-file?path=` | One plan file, raw, with its `revision` ([Plan File](#plan-file)) |
| `PUT /api/mission/runners/:id/plan-file` | Save it (`path`, `content`, `revision`) |
| `POST /api/mission/runners/:id/start`, `/resume` | Run (resume requires `paused`) |
| `POST /api/mission/runners/:id/pause` | Pause, with optional `mode` |
| `POST /api/mission/runners/:id/resolve` | Answer a blocker |
| `POST /api/mission/runners/:id/reconcile` | Look for the outstanding operation's receipt |
| `DELETE /api/mission/runners/:id` | Remove the runner |

Prompt, callback and history routes are listed in
[Runner Prompt Templates](runner-prompts.md), [Runner Callback Scripts](runner-callbacks.md) and
[Runner History](../components/runner-history.md).
Queue writes take the revision they read; there is no whole-array write, so a caller cannot mark
an item done by replacing the list.

`GET /api/mission/runners/:id/queue` returns canonical rows/revision, `execution` and `scheduler`.
`POST /api/mission/runners/:id/start`, `/pause`, `/resolve` and `/reconcile` use the transition
service and return the refreshed snapshot. Public runner payloads expose one `execution` object;
transition-era flat aliases remain internal and are derived from `runner_runtime` and
`runner_operations`, never used as fallback authority.

`DELETE /api/mission/runners/:id` removes the runner row, and deleting a project removes its
runners. Both then call `runner-callbacks.purgeRunnerState`, which deletes the working state no
foreign key reaches: `runner_usage_state`, `runner_queue_observations`,
`runner_quota_recoveries` and `runner_resolutions`. Callback settings, script files, the history
journal and the callback outbox outlive the runner on purpose: the `destroy` callback still has
to run after the row is gone, and the record stays readable. The Mission session and the queue
file are untouched; the session returns to the ordinary listing.

A callback script runs in the control plane, not in the PAD; its working directory and fallback
are described in [Runner Callback Scripts](runner-callbacks.md#execution).
