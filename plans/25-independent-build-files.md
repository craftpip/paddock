# Independent Per-Instance Build Files (plan 25)

## Status: Complete (2026-08-09) — 12/12 progress items done and live-verified
across all five agent types (see regression table). Open questions are
non-blocking.

## Goal

Every agent becomes **completely self-contained**: its build files
(Dockerfile, start.sh, build args) live **inside its own instance folder**, and
it builds its **own image tag**. Nothing is shared between PADs of the same
type anymore.

- On create, the agent's build files are **copied** from the shared template
  (`src/vm-builds/<type>/`) into `instances/<name>/build/`.
- The instance `docker-compose.yml` builds from that per-instance context and
  tags the image per-instance (`paddock-vm-<name>:latest`).
- Editing the build files + rebuilding affects **only that one PAD**. No more
  cross-PAD rebuild side effects, no more forced build args, no more
  reconciliation checks.
- The build file is the **single source of truth** for the image, and it is
  written to be **easy to add/remove content** (marked sections, optional
  blocks, `build.env` toggles, an `extras/` drop-in folder).

**Why:** today a rebuild for one PAD rebuilds the shared
`paddock-vm-<type>:latest` for *every* PAD of that type, so `updateAgent()`
must force-append `INSTALL_DOCKER=1` and the settings route must probe the
running image for the docker CLI (`imageHasDockerCli`) to decide whether a
rebuild is needed. All that bookkeeping disappears when each PAD owns its
image.

## Current behavior (verified 2026-08-08)

- **Shared build dirs** `src/vm-builds/<type>/{Dockerfile,start.sh}` are the
  `build.context` for every instance of that type. `generateInstanceCompose()`
  emits `context: ${WORKSPACE}/instances/${name}/${driver.buildRel}` which
  resolves back to `/workspace/src/vm-builds/<type>` (`vm-manager.js:96`).
- **Shared image tags** `paddock-vm-<type>:latest` come from
  `driver.buildImage` (`vm-manager.js:87,197`; `app.js:885,965`).
- `createVm()` writes meta.env + compose, then `docker compose build` + `up`.
  It **never copies** build files into the instance dir.
- `updateAgent()` (`vm-manager.js:293`) force-adds
  `driver.installDockerBuildArg` (`INSTALL_DOCKER=1`) to the build args on
  every rebuild — the comment there says why: the image is shared, so a
  rebuild must keep baking docker or every other PAD that enabled it silently
  loses the CLI.
- Settings route (`app.js:976`) computes `needRebuild = newAllow && !oldAllow
  && !(await imageHasDockerCli(name, image, wasRunning))` — probing the image
  at runtime because the CLI availability is not self-describing.
- Drivers hardcode `buildImage` and `buildRel` (`openclaw.js:26-27`,
  `opencode.js:22-23`, `picoclaw.js:22-23`, `hermes.js:22-23`,
  `codex.js:22-23`). `currentVersion(name)` falls back to
  `docker run --rm <buildImage>` — the shared tag.
- Clone mode copies only the source agent **data dir**, not any build files.

## Design

### Per-instance build folder

```
instances/<name>/build/
├── Dockerfile      # copied from src/vm-builds/<type>/Dockerfile — fully editable
├── start.sh        # copied — the container entrypoint (when the type has one)
├── build.env       # optional K=V ARG overrides; machine-generated by toggles,
│                   #   hand-editable too. # comments allowed.
└── extras/         # optional drop-in assets (scripts, debs, configs)
                    #   COPY'd by the Dockerfile template when present
```

The shared `src/vm-builds/<type>/` becomes the **template source** only — read
once at create/clone/migrate time to seed the instance copy. After that the
instance build dir is the only thing that matters for that PAD.

### Per-instance image tag

`imageFor(name)` = `paddock-vm-<name>:latest` (e.g.
`paddock-vm-pad-opencode-yo:latest`). Small shared module
`src/services/instance-image.js` exporting `imageFor(name)` so drivers,
vm-manager and app.js all derive the same tag. Name never changes → the tag is
stable; nothing needs persisting in meta.env.

### Self-describing build args (the "easy add/remove" core)

To keep "all changes live in the build file", the compose `args:` block is
**generated from the instance's own Dockerfile**:

- `generateInstanceCompose()` reads `instances/<name>/build/Dockerfile`,
  extracts every `ARG <NAME>` line, and emits:
  ```yaml
  build:
    context: /workspace/instances/<name>/build
    args:
      INSTALL_DOCKER: ${INSTALL_DOCKER:-0}
      INSTALL_TMUX: ${INSTALL_TMUX:-1}
  ```
- Every Compose invocation for the instance passes its `build.env` as an
  env-file: `docker compose --env-file instances/<name>/build/build.env -f
  <compose> ...`. This includes `build`, `up`, `config`, reset, settings, web
  publishing, and health checks, so Compose always resolves the same build
  configuration.
  Editing an ARG value in `build.env` takes effect on the next build with
  **zero compose regeneration**. Adding/removing an ARG in the Dockerfile is
  picked up the next time the compose is regenerated (create, settings, web
  publish, reset — all funnel through `generateInstanceCompose()` already).

### Dockerfile template — marked, removable sections

The per-type templates are rewritten into clearly delimited blocks with a
banner header explaining this is a per-instance file. Each block is a
self-contained unit the user can add/remove by deleting or uncommenting it:

```dockerfile
# ============================================================
# <TYPE> agent image — THIS PAD's own build file
# Lives in instances/<name>/build/ and builds only this PAD.
# Edit freely. Rebuild: Settings → Update.
# ============================================================

# ---- 1. BASE -------------------------------------------------
FROM ghcr.io/openclaw/openclaw:latest

# ---- 2. BUILD ARGS (override values in build.env) ------------
ARG INSTALL_DOCKER=0
ARG INSTALL_TMUX=1

# ---- 3. SYSTEM TOOLS — add/remove package names here ---------
RUN apt-get update && apt-get install -y --no-install-recommends \
    openssh-server \
    tmux \
    jq \
    # ^ ADD or REMOVE package lines above this point
    && rm -rf /var/lib/apt/lists/*

# ---- 4. OPTIONAL: docker CLI (build.env INSTALL_DOCKER=1) ----
RUN if [ "$INSTALL_DOCKER" = "1" ]; then \
      apt-get update && apt-get install -y --no-install-recommends docker.io && \
      rm -rf /var/lib/apt/lists/*; \
    fi

# ---- 5. OPTIONAL: extras/ drop-in (delete block if unused) ----
COPY extras/ /opt/extras/
# Uncomment to run extra setup on build:
# RUN bash /opt/extras/setup.sh

# ---- 6. APP / CLI install ------------------------------------
RUN npm config set fund false && npm config set audit false && npm install -g <app>

# ---- 7. ENTRYPOINT -------------------------------------------
COPY start.sh /usr/local/bin/start.sh
RUN chmod +x /usr/local/bin/start.sh
ENTRYPOINT ["/usr/bin/tini", "-s", "--", "/usr/local/bin/start.sh"]
```

Rules for the templates:

- Every block is separated by a `# ---- N. NAME ----` banner with a one-line
  "what to edit here" comment.
- Feature toggles are ARGs with sane defaults (`INSTALL_DOCKER=0`,
  `INSTALL_TMUX=1`), overridable per-instance via `build.env`.
- `extras/` is a convention, not magic: the template includes the
  `COPY extras/ /opt/extras/` line (harmless when the folder is empty — Docker
  skips? no, COPY fails on a missing source, so **create always seeds an empty
  `extras/` dir** with a `.gitkeep`). Adding a file = drop it in `extras/` +
  reference it; removing = delete the block.
- `start.sh` stays a separate copied file (keeps runtime entry logic out of the
  Dockerfile), including the existing web-hook sourcing block. OpenClaw is
  normalized first by extracting its current inline script into the template's
  `start.sh`; this extraction must preserve its current entrypoint behavior.

### Create flow (`createVm`)

1. mkdir instance dir as today.
2. **Copy build template**: `fs.cpSync(src/vm-builds/<type>/, instances/<name>/build/, { recursive: true })`. Seed `extras/` with a `.gitkeep`. Write `build.env` (empty or with driver defaults). Extract OpenClaw's currently inline entrypoint into `src/vm-builds/openclaw/start.sh` before this common copying flow is used.
3. Write `meta.env` (unchanged) + compose. `generateInstanceCompose` now emits
   the per-instance context + `imageFor(name)` + generated `args:` from the
   Dockerfile's ARG lines.
4. Build + up use the instance `--env-file` consistently.
5. Clone mode is allowed only when the source has the **same agent type** as
   the requested PAD. Reject a cross-type clone before copying any files.
   Same-type clones also copy the source instance's `build/` (so they inherit
   customizations), not just the data dir.

### Update flow (`updateAgent`)

- **Delete the force-append logic** (`installDockerBuildArg` driver field, the
  `bargs` loop at `vm-manager.js:304-309`). Rebuild = `docker compose
  --env-file <instance>/build/build.env -f <compose> build <name>`, nothing
  more. The comment explaining shared-image cross-PAD effects is removed — it
  no longer applies. Use the same `--env-file` Compose prefix for the following
  recreate command and every other Compose command for this instance.
- `pull: false` callers (settings docker-rebuild path) stay supported.

### Settings docker toggle (`app.js` settings route)

- `image` in the GET payload → `vm.imageFor(name)` (was `driver.buildImage`).
- The `needRebuild` probe stays (cheap, per-instance image now), but the fix
  becomes self-describing: persist the requested state in
  `instances/<name>/build/build.env` via `vm.setBuildEnv(name, {
  INSTALL_DOCKER: newAllow ? '1' : '0' })`. When enabling an image without the
  CLI, then call `updateAgent(name, { pull: false })`; the rebuild picks the
  value up from the env-file — no ad-hoc `--build-arg` passed by the route.
- Turning docker **off** writes `INSTALL_DOCKER=0` for the next rebuild, but
  does not uninstall the CLI from the existing image. The toggle immediately
  controls the socket mount; a later rebuild applies the persisted build value.
  This matches today's behavior.

### Driver changes

- Rename `buildRel` → `templateDir` (same path, clearer meaning: the
  create-time copy source). Remove `buildImage` and
  `installDockerBuildArg` from every driver.
- `currentVersion(name)` fallback (`docker run --rm --entrypoint <bin> …`)
  uses `imageFor(name)` instead of the removed `buildImage`.
- app.js `:885` (settings GET) and `:965` (settings POST) use
  `imageFor(name)` instead of `driver.buildImage`.
- New helper `setBuildEnv(name, kv)` + `readBuildEnv(name)` in vm-manager
  (or `instance-image.js` companion `build-env.js`) — read/write
  `instances/<name>/build/build.env` preserving comments and other keys.

### Migration of existing PADs (one-time)

Existing PADs have no `build/` dir and run the shared-type image. On webui
start (or an explicit `GET /api/admin/migrate-builds` button), run
`ensureInstanceBuilds()` — idempotent:

1. For each instance missing `build/`: copy the template from
   `src/vm-builds/<type>/`, seed `extras/`, write `build.env` with
   `INSTALL_DOCKER=<current meta DOCKER>`.
2. **Retag, don't rebuild**: `docker tag paddock-vm-<type>:latest
   paddock-vm-<name>:latest` — the running image is preserved instantly.
3. Regenerate the compose (per-instance context + image + args) and
   `--force-recreate` so the container now runs under its own tag. Recreates
   are cheap (same image ID).
4. Optionally `docker rmi` old shared `paddock-vm-<type>:latest` once no
   instance references it.

Because step 1 seeds from the same template the shared image was built from,
the retagged image and the instance build files start **in sync** — an Update
rebuild later produces an equivalent image.

### Health check / other consumers

- `container-health.js` compares declared compose image vs actual inspect —
  both now derive from `imageFor(name)`; no code change needed, it just
  becomes per-PAD accurate. It also checks the compose `build.context` — now
  the instance dir; fine.
- `container-health`/registry `meta.OPENCLAW_VERSION` usage unchanged.
- Docker layer cache keeps per-instance rebuilds fast (base + apt layers are
  shared on disk across images; only the final layers differ per PAD).

## Verification

```bash
# unit
docker exec paddock node --test test/services.test.js

# live — create a fresh PAD, confirm self-containment
docker compose -f instances/pad-t1/docker-compose.yml config
#   build.context = .../instances/pad-t1/build  (NOT src/vm-builds/...)
#   image = paddock-vm-pad-t1:latest
ls instances/pad-t1/build            # Dockerfile, start.sh, build.env, extras/
docker inspect pad-t1 --format '{{.Config.Image}}'   # paddock-vm-pad-t1:latest

# customize + rebuild affects ONLY this pad
#   edit instances/pad-t1/build/build.env  INSTALL_TMUX=0
#   (or edit the Dockerfile, add a package) then Settings → Update
docker exec paddock node -e "..."    # or browser: Settings → Update
docker exec pad-t1 sh -c 'command -v tmux; command -v jq'
docker exec pad-other-type-agnostic... # ANOTHER pad of the same type is untouched
#   docker images --format '{{.Repository}}:{{.Tag}}' | grep paddock-vm   → per-pad tags

# docker toggle self-describing
#   Settings → toggle "Allow docker" on a pad whose image lacks the CLI
#   → instances/<name>/build/build.env contains INSTALL_DOCKER=1, rebuild happens
#   → only that pad's image changes

# migration
#   stop webui, wipe one pad's build/ + retag simulate → restart webui
#   → ensureInstanceBuilds() restores build/, image tag = paddock-vm-<name>:latest,
#     container recreated, no behavior change

# clone
#   create from source with a custom build/ → clone gets the same custom files
#   and its OWN image tag

# no more cross-pad coupling
#   rebuild pad A (update) → docker inspect pad B (same type): image + layers
#   unchanged, uptime not restarted
```

## Open questions

- **`start.sh` duplication**: it lives both in `build/` (baked into the image
  at build) and `instances/<name>/<agent>/start-web.sh` (runtime web hook).
  Keep both as-is — they serve different layers (image entrypoint vs runtime
  hook) — or fold the web hook into the per-instance `start.sh`? Prefer keep
  separate (hook changes should not need an image rebuild).
- **Shared `monitor` build dir**: `src/vm-builds/monitor/` has no driver and
  isn't an agent type — leave it shared/untouched.
- **Update UX for "reset to template"**: once an instance build file is
  edited, there's no way to get the pristine template back. Add a "Reset build
  files to template" button in Settings (re-copies from `src/vm-builds/<type>`
  + rebuilds)? Nice-to-have; cheap since the copy source still exists.
- **Fleet clones that intentionally share an image**: per-instance images
  multiply disk for large fleets (layers are deduped on disk, so the cost is
  mostly small final layers). If a fleet wants literal identical images later,
  add an opt-in "share image" override (compose `image:` override + a `SHARE`
  meta flag). Not in this plan's scope.
