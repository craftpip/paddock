# Plan 42 — Memory Palace: shared memory for every agent

## Status: Proposed (2026-08-12) — research complete, implementation 0/8.
mempalace (official image, `serve`-over-HTTP mode, bearer token, `/healthz`,
agent-wing model) verified from upstream docs and the repo's
`deploy/docker-compose.server.yml`. The per-driver MCP plumbing this plan
reuses already ships (plan 35b: driver `mcp` builders, `getMcp()` call site,
CommandsPane MCP group). Design below is complete; nothing built yet.

## Goal

Run a **single shared memory palace** as an independent container the webui
starts and manages. The container runs mempalace's MCP server over HTTP, and
every PAD agent connects to it, so **all agents share one persistent memory**:
cross-session and cross-agent. Each agent gets its own wing + diary inside the
shared palace (mempalace's native agent model), so memory is shared yet
structured — and searchable with the palace metaphor (wing → room → closet →
drawer, plus cross-wing tunnels and a temporal knowledge graph).

## Context: what already exists

Plan 35b shipped the entire per-driver MCP machine this plan rides on:

- Every driver has an `mcp` object with `buildConnect/buildDisconnect/
  buildInspect/buildTest` returning fully shell-quoted commands, plus
  `serverName: 'paddock'` and the `read -rsp` key bootstrap in
  `src/services/drivers/mcp-util.js` (`bootstrap()`, `sq()`).
- `src/services/drivers/index.js` `getMcp(type, url)` serializes it; the
  CommandsPane MCP group renders the pills (Connect Paddock MCP / List / Test /
  Disconnect); `GET /api/agents/:name/mcp` lists configured servers as chips.
- `src/services/paddock-mcp.js` computes the webui's own MCP URL from
  `HOST_NAME`/`HOST_PROTO`/`WEBUI_PORT` (`PADDOCK_MCP_URL` overrides).

Per-driver MCP shapes (streamable-http + bearer) were live-verified for all six
types in plan 35b §3/§3b — this plan reuses that matrix verbatim with a
different server name and URL.

## Design

### 1. The mempalace container

- **Container name:** `${CONTAINER_PREFIX}-mempalace` (e.g. `pad-mempalace`).
  Not a PAD: excluded from agent discovery, not user-deletable via the agent
  UI, never gets a per-PAD image build.
- **Image:** `ghcr.io/mempalace/mempalace:latest`, pulled once on first start.
- **Palace data:** host bind `/www2/paddock/src/data/mempalace` → container
  `/data` (uid 1000 ownership — same as `src/data/app.db*`, keep the ownership
  rule). Compose file `src/data/mempalace/docker-compose.yml` generated by the
  webui using **absolute host paths** (the `HOST_WORKSPACE_ROOT` rule).
- **Run:** `serve --host 0.0.0.0 --port <MEMPALACE_PORT>` with **chroma backend**
  (embedded, single container — decided; Qdrant only if we outgrow it). Env:
  `MEMPALACE_MCP_HTTP_TOKEN` (required), `MEMPALACE_EMBEDDING_DEVICE=auto`.
  **Embedding model (decided):** default all-MiniLM-L6-v2 (~30 MB, English) —
  the image's built-in default, no extra config; switch to embeddinggemma-300m
  later via `embedding_model` config + `mempalace repair rebuild-index` only if
  we need multilingual memory.
- **Port:** `MEMPALACE_PORT` in `.env`, default 8765, checked with
  `hostPortInUse` before bind; `MEMPALACE_URL` overrides the agent-facing URL
  (mirrors `PADDOCK_MCP_URL`).
- **Health:** rely on `GET /healthz`; `restart: unless-stopped` so the webui's
  own crash doesn't kill the palace.

### 2. The webui service (`src/services/mempalace.js`)

A small service (door-shaped, like `vm-manager`'s socat door) owning the whole
lifecycle:

- `statusMempalace()` — container state (`docker ps` cache), healthz probe,
  image/version, port, data-dir size.
- `ensureMempalace()` / `startMempalace()` / `stopMempalace()` /
  `restartMempalace()` — write the compose if missing, then `docker compose up
  -d` / `down` inside the paddock container (compose CLI lives there).
- `removeMempalace()` — stop + `docker image rm ghcr.io/mempalace/mempalace`
  and data-dir removal, both behind confirm; reuse the root-helper trick if the
  palace data ends up root-owned.
- `rotateToken()` — new `MEMPALACE_MCP_HTTP_TOKEN`, restart, notify the UI
  that agents must reconnect.
- `getMempalaceUrl()` — `http://<HOST_NAME>:<MEMPALACE_PORT>/mcp`
  (`MEMPALACE_URL` override), mirroring `paddock-mcp.js`.

Routes in `app.js` (owner/admin scoped, CSRF on POSTs):
`GET /api/mempalace` (status + config), `POST /api/mempalace/start|stop|
restart|remove`, `POST /api/mempalace/token/rotate`. Read-only GETs stay
frontend-safe; actions are POSTs.

### 3. Shared-memory model across agents

- One palace, many agents. mempalace's agent model gives each specialist agent
  **its own wing + diary** inside the shared palace — that's the "shared yet
  separated" default (matches upstream guidance). `mempalace_list_agents`
  discovers members at runtime, no system-prompt bloat.
- Cross-agent sharing = the palace itself: any agent can `mempalace_search`
  anything, walk tunnels, and read another agent's diary when the wing policy
  allows. Tunnels are the explicit "this room connects to that room" primitive.
- **No per-agent palace dirs** (the naive isolation the MCPWorks article
  suggests) — the whole point of this plan is one shared store.
- Optional stretch (not in v1): mount agent data dirs into the mempalace
  container read-only so it can `mine` conversations/workspaces; wire the
  Claude Code / Codex auto-save hooks inside agent containers.

### 4. Agent integration (per-driver connect)

Agents reach the palace over LAN at `http://<HOST_NAME>:<MEMPALACE_PORT>/mcp`,
same reachability answer plan 35b verified (`10.69.1.164` from every agent
container). Wire-in follows the paste-commands rule: a **Memory Palace group in
the CommandsPane** whose pills paste the driver's connect/disconnect/list/probe
commands into the docked terminal.

Reuse the plan 35b builders rather than duplicating six drivers: generalize
each driver's `mcp` builders to take `{ url, name, tokenEnv }`
(`name`/`tokenEnv` default to `paddock`/`PADDOCK_MCP_TOKEN`), then serve a
second block per type from `/api/agent-types/:type/commands` (an `mempalace`
key next to `mcp`) with the mempalace URL/name. Per-driver matrix (from plan
35b §3, swap server name):

| Driver | connect shape |
|--------|---------------|
| openclaw | `openclaw mcp add mempalace --url <u> --transport streamable-http --header "Authorization=Bearer $TOKEN" --no-probe` |
| opencode | `opencode mcp add mempalace --url <u> --header "Authorization=Bearer $TOKEN"` (no probe flag; removal = config edit) |
| picoclaw | config patch `tools.mcp.servers.mempalace` (no MCP CLI in v0.2.5) |
| hermes | config.yaml patch `mcp_servers.mempalace` → url + `headers.Authorization` |
| codex | `codex mcp add mempalace --url <u> --bearer-token-env-var MEMPALACE_MCP_TOKEN` (+ config.toml header patch) |
| claude | `claude mcp add --transport http --scope user mempalace <u> --header "Authorization: Bearer $TOKEN"` |

**Secret handling (decided):** backend-triggered connect, not a pasted
command. Every driver builder already references the token only as an env var
(`$PADDOCK_MCP_TOKEN`), never inline — so the webui execs the **same**
live-verified builder output headlessly (docker exec) with the token injected
as an env var. The token therefore never appears in a command string, terminal
history, job log, toast, or API response. Precedent: the Vault is already the
documented "server-side secrets" exception to the paste-commands rule
(AGENTS.md). The manual path remains: a "Connect (manual key)" pill pastes the
builder with a `read -rsp` prompt for users who want the visible-terminal flow.
Rotation = new token + restart palace; agents reconnect by re-running connect.

### 5. UI surface

- **Settings → Memory Palace card:** status (running/stopped, port, version,
  healthz), Start / Stop / Restart / Remove, token rotate, "copy connect URL",
  first-run note about the embedding-model download (~30–300 MB).
- **CommandsPane → Memory group** (per driver, like the MCP group): Connect /
  Disconnect / List servers / Probe mempalace, plus a "Connect (manual key)"
  fallback pill (`read -rsp`). Chips reuse `GET /api/agents/:name/mcp` if it
  already lists the `mempalace` entry.
- **Auto-connect (decided):** a "Shared memory" checkbox in the Create form and
  a matching per-agent toggle in Settings, **default ON** — new agents join the
  palace automatically at the end of create (backend-triggered connect), while
  `test-agents` and sandbox PADs can opt out. Disconnect removes the server.
- Optional stretch: a read-only "Memory" tab on the agent page browsing the
  agent's wing (list wings/rooms, search). Not required for shared memory to
  work.

### 6. Lifecycle & safety

- Lazy start on first "Start Memory Palace" click; `MEMPALACE_AUTO_START=true`
  opts into boot-time start (default off — first run downloads a model and
  starts an extra container).
- Stop never deletes data; Remove deletes the palace (confirm + the
  root-owner helper path). Token rotation is non-disruptive to stored memory.
- The palace container is **paddock-managed infra** — never touched by hand,
  never listed as an agent (exclude `-mempalace` from discovery), never
  deleted by `pruneDanglingImages` (it's a pulled image, not a per-PAD build).
