# 2026-10-11 — the pad_* tools drop mid-session, and the fix

**Date:** 2026-10-11
**Mode:** chat test (MCP only) — with a stated deviation: at the user's explicit
request, the cause of the dropped `pad_*` surface was diagnosed out of band
(host `curl` probe of the pad MCP endpoint + the opencode client's own
`opencode mcp list`), and then **fixed** (ownership) at the user's direction.
The out-of-band steps are recorded here because the tool surface could not
answer any of it.
**Task:** user: *"what is the error for mcp failing now?" → "yes chek error is
api key expired?" → "debug your mcp setup why pad is not working, after changes
tell me i will restart this session"*

Outcome: `pad_*` tools worked for a full verify pass, then vanished mid-session.
The API-key hypothesis is **false**. The log evidence splits the problem into
two **independent** defects that were easy to conflate:

1. A harness **ownership** defect: a root `opencode web` process and the
   uid-1000 TUI share `/root/.local/state/opencode` (uid 1000 has `HOME=/root`),
   the root side owned `locks/`, and the node-side client's registration CLI
   (`opencode mcp list`) failed with the `PermissionDenied … locks/…lock` plan69
   recorded. **Fixed** by chowning the state dir and `friction/` to uid 1000.
2. A running-session **client** behavior: opencode fetches MCP tools once per
   process and, once a server is marked `server unavailable … status=failed`,
   retries for only ~1.5 s and never re-fetches until the process restarts.
   There is no reload/reconnect action in the client surface (CLI, keybinds,
   docs), and a config hot-reload test produced no event in the live session's
   log. A fresh opencode process now registers and calls `pad_health` cleanly —
   restarting the TUI is the supported way back, and it now reliably works.

## Findings

### When the pad MCP connection dies, opencode surfaces no error

- **Tool:** whole `pad_*` surface (negative) + the `opencode` client
- **Severity:** blocker
- **What I asked:** after a full verify pass, a routine `pad_list_agents`.
- **What happened:** every `pad_*` call returned, verbatim:
  `Model tried to call unavailable tool 'pad_list_agents'. Available tools: bash,
  edit, glob, grep, invalid, question, read, skill, task, todowrite, webfetch,
  websearch, write.` No pad tool registered any more; no MCP-level error, no
  `401`, nothing — opencode just stopped advertising the tools minutes after
  they worked.
- **Why it hurts:** the caller cannot tell "server down" from "key revoked" from
  "connection dropped". The only diagnostic is *"unavailable tool"*, a symptom,
  not a cause.
- **Fix:** opencode should surface the remote server's last error when a
  registered MCP server stops responding, rather than silently dropping the
  namespace.

### The API key is fine — only an out-of-band probe could show it

- **Tool:** host `curl` probe of `http://10.69.1.164:6789` (configured `pad` MCP
  server), run at the user's request; key read from config, never quoted.
- **Severity:** guessing
- **What I asked:** is the drop an expired API key?
- **What happened:** `GET /` → `200`; `POST /mcp` initialize **with** the key →
  `serverInfo: paddock v1.0.0`, `tools.listChanged`, and `tools/list` returns the
  full 31-tool catalog (no `task_*` family — the `PADDOCK_TASK_QUEUE` gate is
  off, matching plans). Without the key → `401`. Key valid, server healthy,
  tools served; the absence is purely client-side.
- **Why it hurts:** the only way to learn any of this was to leave the MCP
  surface entirely. An MCP-only caller cannot distinguish an expired key from a
  dead server from a dropped connection — the user's first guess was wrong and
  nothing in-session could correct it.
- **Fix:** opencode should echo the server's actual status (401/refused/timeout)
  when a remote MCP server misbehaves.

### The drop is opencode's sticky "server unavailable" — and separately, the root-owned `locks/` is real and fixed

- **Tool:** `/usr/local/bin/opencode mcp list` (client diagnostic) + the client's
  own log (`/root/.opencode/data/opencode/log/opencode.log`) + `ps` + `ls` +
  a config hot-reload experiment
- **Severity:** blocker (both threads verified)
- **What I asked:** reproduce, then locate, the failure.
- **What happened:** two distinct defects, each with its own evidence.

  *Thread A — root-owned state dir.* Two opencode processes run as different
  users over the same state dir because uid 1000 has `HOME=/root`: root runs
  `opencode web --port 7890` (up since Oct 10), node runs the interactive TUI.
  The root side owned `…/state/opencode/locks/` (drwxr-xr-x root:root), and the
  node side's `opencode mcp list` reproduced plan69's error verbatim:
  `PermissionDenied: FileSystem.makeDirectory (…/locks/…lock)`. The Oct 8 chown
  had been undone — `locks/` was re-minted root:root.

  *Thread B — the live mid-session drop.* The TUI started (22:04Z) **while**
  `locks/` was already root-owned yet registered pad tools fine, so the lock was
  NOT what dropped the session. The client log shows the three active remote
  servers failed simultaneously at 2026-10-10T22:17:08Z
  (`message="server unavailable" key=browser|paddock|pad type=remote
  status=failed`) — a transient server/network blip, since the same endpoint
  answered the headless probe minutes later. opencode retried only
  22:17:34–22:17:36 (~1.5 s) and then never re-fetched, even after the chown
  hours later. No `reload`/`reconnect` exists in `opencode mcp` (only add, list,
  auth, logout, debug), in the keybinds (only an `mcp_list` dialog, default
  `none`), or in the docs. A config hot-reload test (`pad.enabled` false→true in
  `opencode.json` → no event in the live run's log) confirmed the running
  process does not re-read MCP config.
- **Why it hurts:** the caller cannot distinguish the two. The lock error looks
  like "MCP broke," and the drop looks like "MCP broke," but only one of them is
  fixable at the harness level. The other is a client lifecycle rule — fetch MCP
  tools once per process, mark failed, never retry — that surfaces to the user
  only as the same "unavailable tool" symptom.
- **Fix:** Thread A: `sudo chown -R 1000:1000 /root/.local/state/opencode`
  (applied 2026-10-11; verified `opencode mcp list` now reports `browser`,
  `paddock`, `pad` connected) and `sudo chown -R 1000:1000
  /www2/paddock/friction` (applied; touch-probe verified). Thread B: default the
  client to re-fetch a `failed` remote server on a backoff, or expose a
  reload/reconnect action; until then, restart the process — one fresh run was
  verified end-to-end (`pad_health` returned the real health payload). Long-term
  harness fix: the uid-1000 account should not have `HOME=/root`; a node-owned
  HOME (or `XDG_STATE_HOME`) removes the collision class entirely.
