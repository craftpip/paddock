# exec ls on pad "proj"

- **Date:** 2026-09-29
- **Mode:** pad_* tools only (MCP)
- **Task as phrased:** `pad -> proj exec ls`
- **Outcome:** Worked. Ran `ls` in the pad named "Proj" and got a directory listing — but I cannot say from the response *where*.

## Findings

### `pad_exec` never tells you which directory it ran in

- **Tool:** `pad_exec`
- **Severity:** guessing
- **What I asked:** run `ls` inside the pad named "Proj" — no path, so I expected the pad's default.
- **What happened:** `{ "name": "pad-opencode-proj", "stdout": "AGENTS.md\nBOOTSTRAP.md\n...\nyt-dl-auto\n", "stderr": "" }`. Forty-one entries, a flat name list, and not one byte saying where. No `cwd`, no `exitCode`, no echo of the command line.
- **Why it hurts:** The tool description says "Run a shell command inside a PAD container" and nothing about a working directory, so I had to infer the rule — workspace root? `$HOME`? the agent's own project dir? — from the fact that `AGENTS.md`/`SOUL.md`/`IDENTITY.md` are present and no absolute path is anywhere in the payload. A caller who then wants to read one of those 41 entries has to guess what `path` to pass to `workspace_read`. The listing is the answer; the *location of the answer* is the part I needed.
- **Fix:** add `"cwd": "<abs path>"` to the `pad_exec` response, and state the default working directory in the tool description.
- **Resolution (2026-09-29, plan 61):** fixed and verified live. `exec` now returns
  `cwd`, `requestedCwd` and `exitCode`, and takes an explicit `cwd`. The reported
  `cwd` is probed with the SAME `cd` the command received — my first version
  probed a bare `pwd`, which reported the container default while the command had
  run elsewhere, reintroducing the very confusion the field exists to remove (found
  by the live test, not by reading the code). Verified: default `cwd` is `/www1`;
  `cwd: /www1/craftpip.com` runs and reports there; a bad `cwd` exits 2 with nothing
  run instead of silently landing somewhere else. The value is shell-quoted because
  it is caller-controlled and interpolated into `sh -lc`.

### "proj" is two pads, and only one of them is named that

- **Tool:** `pad_list_agents` + `pad_exec`
- **Severity:** guessing
- **What I asked:** act on the pad called "proj".
- **What happened:** `list_agents` returned both `pad-opencode-proj` (`"display_name": "Proj"`) and `pad-proj2` (`"display_name": "Proj2"`). Nothing in the fleet listing says which one a caller who says "proj" means, and `pad_exec` accepted a name without complaint either way — I picked the exact `display_name` match and said nothing about the guess.
- **Why it hurts:** The listing hands me a human label (`Proj`, `Proj2`) and the tool takes only a container name (`pad-opencode-proj`, `pad-proj2`), so the label I read off the list is not the string I'm allowed to pass. I bridged that gap by eye. A near-miss on a shared prefix (`pad-proj` is not a pad; `pad-proj2` is) is the cheapest possible way to run a command on the wrong agent, and nothing would have warned me.
- **Fix:** let `exec` (and the other `name`-taking tools) resolve an exact `display_name` as well as the container name, and refuse a name that is a substring of exactly one existing pad with a `did you mean pad-proj2?` hint.
- **Resolution (2026-09-29, plan 61):** fixed and verified live. One shared
  resolver backs every `name`-taking tool — exact container name, the bare name
  `create_agent` itself accepts, exact `display_name`, and a UNIQUE substring. So
  the label read off the listing is now a string the tools accept:
  `Proj` → `pad-opencode-proj`, `Proj2` → `pad-proj2`. Genuine ambiguity refuses and
  names every candidate instead of picking one. One precedence rule matters: a
  **prefixed exact match beats substring ambiguity**, so `proj` resolves to
  `pad-opencode-proj` (it is that pad's exact bare name) instead of being rejected
  as ambiguous between it and `pad-proj2`. Resolution runs BEFORE the grant check
  and every grant uses the resolved name, so this does not widen a key's reach.
